# 서버 맞춤 안내서 — 이 서버의 Claude 가 먼저 읽는 곳

[English →](SERVER-GUIDE.md)

> 상황판 코드는 어느 서버나 같다. **서버·솔루션마다 다른 것은 아래 파일의 값으로만** 맞춘다 — 코드를 고치면 새 판을 받을 때 충돌한다.
> 서버 방(`~/dev-server`)과 솔루션 방이 «이 값은 어디서 바꾸지?», «상황판에 이렇게 나오면 무엇을 하라는 거지?» 를 이 한 장에서 찾는다.
> 설치는 [AI-SETUP-PROMPT](AI-SETUP-PROMPT.ko.md), 하루 운영은 [OPERATIONS](OPERATIONS.ko.md), 팀원은 [TEAM-GUIDE](TEAM-GUIDE.ko.md).

## 1. 서버마다 다른 것 — 어디에 있고 누가 바꾸나

| 무엇 | 파일 | 바꾸는 방 | 바꾼 뒤 |
|---|---|---|---|
| 주인 이름·언어·시간대·포트·접속 명령·서버 이름(인증 앱 항목) | `~/dev-server/board/config.json` (예: `config.example.json`) | 서버 방 | `pm2 restart dev-board` |
| 솔루션 목록과 솔루션별 버튼·배포·문의·표식 | `~/dev-server/projects.json` (2절) | 서버 방 | 저장하면 바로(다시 켤 필요 없음) |
| 솔루션이 쓰는 외부 서비스(키 이름만) | `~/dev-server/services.json` | 서버 방 | 바로 |
| 이 서버 모든 Claude 의 일하는 방식 | `~/.claude/CLAUDE.md` | 서버 방(주인 지시로) | 새 방부터 |
| 솔루션 하나의 규칙·빌드·재시작·배포·문의 읽기·답글 길 | `<솔루션>/CLAUDE.md` «개발 명령 설정» 절 | **그 솔루션 방** | 새 방부터 |
| 솔루션 개발 명령(/개발시작 …) | `<솔루션>/.claude/commands/` | 그 솔루션 방 | 바로 |

- 서버 방은 솔루션 폴더 안을 고치지 않는다. 솔루션 쪽이 바뀌어야 하면 그 솔루션 대기열에 넣는다(`POST /api/rooms {"project":"<키>","task":"…","queue":true}`).
- 비밀값(.env·토큰·DB 비밀번호)은 어느 파일에도 쓰지 않는다 — **어디 있는지만**.
- **📎 첨부**(일 시키기·💬 상의에 붙인 사진·파일): 솔루션마다 `<솔루션>/.claude/attach-tmp/<날짜>/` 임시 칸(그 안 `.gitignore` 가 `*` — git 에 안 섞임). 올린 지 `config.json` `attachKeepDays`(기본 7, 1~90)일 지나면 상황판이 지움 · 한 번도 안 보낸 것은 하루 · 대기열·제안에 걸린 것은 남김. 일 글 끝에 «[📎 첨부 N개 …]» 경로 목록이 붙어 오면 방은 Read 로 보고, **이 일 뒤에도 쓸 파일만** 솔루션 안 알맞은 폴더로 복사해 두고 보고에 어디 뒀는지 한 줄 — 참고만 했으면 그대로 둔다. 한 파일 25MB·한 번에 8개 · 방(AI)은 첨부를 올리거나 붙일 수 없음.

## 2. `projects.json` 칸 — 하나씩

필수: `key`(영문 소문자 · 대기열·질문에 쓰는 이름) · `name`(화면 이름) · `dir`(솔루션 폴더) · `stateFile`(작업기록, 보통 `.claude/session-state.md`).

| 칸 | 값 | 켜지는 것 | 없으면 |
|---|---|---|---|
| `devUrl` | 개발 주소 | 보고 «확인할 곳» 링크 | 링크 없이 글로만 |
| `noDevDone` | `true` | **개발완료** 버튼 숨김 | 버튼 보임(그 솔루션에 `/개발완료` 명령이 있어야 함 — `kit/verify.sh` 가 맞춰 봄) |
| `prodLabel` | 예 `"MyApp 운영"` | **배포** 버튼(솔루션 키를 쳐야 열림) · 정기 점검 «배포» | 카드에 **«운영 배포 · 연결 안 됨»** — 주인이 누르면 연결 창(아래 «배포 연결») |
| `deploy` | `{command, dryRun, prep, timeoutMin, minMemMb, rollback, extraScripts}` | 상황판이 배포 명령을 **직접** 실행(주인이 화면에서 승인한 명령만 — 바뀌면 다시 승인) · `dryRun`=시험 배포 인자 · `prep:true`=배포 전 AI 준비 방 · `minMemMb`=남은 메모리가 이만큼일 때만 · `timeoutMin`=넘으면 멈춤 · `rollback`=실패 때 보여 줄 되돌리기 안내(실행 안 함) · `extraScripts`=바뀌었나 지문만 볼 스크립트 | AI `/배포` 방이 배포 |
| `routineDeploy` / `manualDeploy` | 배포 한 줄(폴더 기준 / 절대 경로) | «AI 없이 직접 배포» 안내에 보일 명령 | «배포 명령이 등록되지 않음» |
| `deployScripts` | 배포 스크립트 경로 목록 | 그 스크립트가 도는 동안 «배포 중» 표시·다른 배포 막기 | 표시 없음 |
| `cleanDeploy` | `true` | 배포 스크립트가 «마지막 커밋의 깨끗한 사본» 에서 나간다고 봄(일시정지·임시 저장 단계 생략) | 하던 일을 잠깐 치우고 배포 |
| `prodMarker` | `{url, json:"<칸>"}` 또는 `{url, header:"last-modified"}` | 운영 공개 주소에서 «마지막 운영 배포 시각» 을 읽어 «운영에 아직 없음» 을 가림 | 운영 반영 여부를 모름 |
| `inquiries` | 켜기 — 그 솔루션 개발시작 명령 안 문의 읽기 절의 제목을 적어 두면 좋다(상황판은 있고 없음만 봄) | 카드 «✉ 들어온 문의» 칸 · 정기 점검 «문의 가져오기» | 문의 칸·문의 가져오기 없음 |
| `feedbackTriage` + `prodSsh` + `prodDir` | 조사 절 제목 · 운영 접속 · 운영 폴더 | 접수된 피드백을 AI 가 미리 조사(읽기 + 조사 칸만 씀) | 조사 없음 |
| `devLogin` | `true` | «시험 계정으로 열기» 버튼(`kit/DEV-LOGIN.md`) | 버튼 없음 |
| `batch` | 1~5 | 작은 일을 한 방에 묶어 보냄 | 하나씩 |
| `scout` | 0~n | 고치는 방과 따로 읽기만 하는 «정찰 방» 수 | 정찰 없음 |
| `morningCheck` | `true` | (옛 crontab 방식) 아침 점검 대상 — 상황판 «◷ 정기 점검» 은 이 값과 상관없음 | — |

**배포 연결** (2026-11-17) — 카드 «운영 배포 · 연결 안 됨» 또는 연결된 카드 배포 줄 «⚙ 연결 설정» 이 여는 창이 `prodLabel`·`deploy.command`·`deploy.dryRun`·`prodMarker` 네 칸을 projects.json 에 쓴다(주인만 · 저장 = 그 명령 승인 · 옛 파일은 `board/log/projects-<시각>.json` · 배포 준비·진행 중엔 못 바꿈). 명령은 솔루션 폴더 안·git 에 커밋된 실행 스크립트 + 허용 인자(`--auto` `--routine`, 시험은 `--dry-run`)만, 셸 기호 금지. «연결 끊기» = 네 칸 지움(스크립트·운영은 그대로). **운영서버 주소·계정·키는 받지도 저장하지도 않는다** — 그건 그 솔루션 배포 스크립트·서버 설정 안. 방(AI)·팀원은 이 창을 못 쓴다(403) — 방은 스크립트를 만들고 보고에 «상황판 연결 값» 을 적을 뿐.


**값을 더하거나 바꾼 뒤**: `bash ~/dev-server/kit/verify.sh`(✘ 0개) — 켠 버튼마다 명령이 있는지까지 본다.

## 3. 들어온 문의 칸 — 방이 채우는 법 (솔루션 방)

`projects.json` 에 `inquiries` 가 있으면 그 솔루션 개발시작(과 정기 점검 «문의 가져오기»)이 문의 읽기 절을 돌고, **열린 문의 전부**를 상황판에 올린다. 상황판은 보여 주기만 한다 — 이 목록 때문에 방이 열리거나 개발이 시작되지 않는다.

```bash
PORT=$(python3 -c 'import json,os;print(json.load(open(os.path.expanduser("~/dev-server/board/config.json"))).get("port",8800))')   # 상황판 포트 — 서버마다 다름
curl -s -X POST -H 'Content-Type: application/json' -H "Origin: http://localhost:$PORT" --data-binary @- http://127.0.0.1:$PORT/api/inquiries <<'EOF'
{"project":"<키>","checkedAt":"<읽은 시각 ISO>","items":[
 {"ref":"fb#12","kind":"inquiry","at":"2026-11-02","who":"로그인 사용자 · <회사>",
  "title":"기록 줄의 날짜·내용을 고치는 방법 문의","verdict":"답장만 필요",
  "basis":"이미 있는 기능(연필 아이콘) — 화면에서 확인","replied":"아직",
  "next":"초안대로 답장","needsOwner":true,"link":"https://<운영>/admin/feedback?id=12","draft":"안녕하세요 …"}]}
EOF
```

- 부를 때마다 그 솔루션 목록을 **통째로 바꾼다**(닫힌 문의는 저절로 빠짐). 열린 문의가 없으면 `"items":[]`. 운영을 못 읽었으면 `{"project":"<키>","ok":false,"note":"이유"}` — 지난 목록은 두고 «확인 못 함» 만. 상황판이 «답장 보내기»·자동 보내기로 맡긴 «보낸 뒤 닫기» 일이 ✅ 로 끝나면 그 줄은 다음 목록을 기다리지 않고 바로 빠진다(그 뒤 올린 목록에 아직 있으면 다시 보임). 답장 일은 대기열 시작 전 선검사를 거치지 않는다.
- 한 번에 100건 · `title` 120자 · `basis` 200자 · `next` 120자 · `draft` 4,000자. `link` 는 `https://` 만.

| 칸 | 뜻 — 이렇게 쓴다 | 이렇게 쓰지 않는다 |
|---|---|---|
| `title` | **우리 말 한 줄 요약**(무엇을 묻는지) | 고객 글 그대로 · 이름·메일 |
| `verdict` | 다섯 낱말만: `이미 해결` · `개발 필요` · `결정 필요` · `답장만 필요` · `확인 중`(그 밖은 «확인 중» 으로 바뀜) | 새 낱말 |
| `basis` | **왜 이 판단인지** — 커밋·배포·실측·화면 확인 한 줄 | 문의 상태(«접수»)·«AI 조사 없음» 같은 내부 표시만 |
| `replied` | 고객이 받은 것: `아직` · `답함(11-02)` · `자동 접수 메일` | — |
| `next` | 방의 짧은 메모(상황판은 «방 메모» 로 보여 줌) | — |
| `needsOwner` | **주인이 지금 손을 대야 할 때만** `true` — 답장 보내기(초안 있음) 또는 읽고 진행·보류 정하기 | 열린 건 전부 `true`(그러면 우선순위가 사라짐) · 방·대기열이 처리 중인 것 |
| `draft` | `답장만 필요`·`이미 해결` 이고 `needsOwner` 인 줄의 **답장 초안**(보내지 않음). 초안 속 사실(«고쳤습니다»·«환불됐습니다»)은 실측한 것만 | 확인 안 한 약속 |
| `queueRef` | 개발로 넘겼으면 대기열 번호(`ref`) | — |

상황판은 줄마다 **«👉 할 일»** 을 같은 말로 풀어 보여 준다 — 방이 문구를 맞출 필요는 없다:
- 초안이 있는 줄 = **답장 보내기**: ① 줄에 바로 있는 «답장 보내기»(주인만 — 초안을 확인 창에 그대로 보여 주고, 확인하면 그 솔루션 대기열에 «이 초안 그대로 답글» 일이 들어감 · 옆 «보낸 뒤 완료로 닫기» 체크는 `이미 해결`·`답장만 필요` 면 기본으로 켜짐) ② «초안 복사» → «관리자 화면 열기» 에 붙여 넣고 저장.
- **답장 자동 보내기**(문의 칸 맨 위 · 주인만 · 솔루션마다 · 기본 끔): «이미 해결» 만 / «이미 해결»·«답장만 필요» 를 고르면 목록이 올라오는 대로 해당 줄(초안 있음·`needsOwner`)을 위 ①과 같은 일로 넣는다(완료로 닫기 포함 · 일 글에 «주인이 안 읽음 — 사실을 운영 기록과 하나하나 대조»). 한 문의에 자동은 한 번만(초안이 바뀌어도 두 번째는 버튼으로). 켤 때 지금 목록에도 바로 적용. 그래서 방은 `verdict` 를 실측대로만 쓴다 — 자동이 켜진 솔루션에선 `이미 해결` 이 곧 «보냄» 이다.
- 초안이 없는 `needsOwner` 줄 = **읽고 정하기**: 관리자 화면에서 진행·보류·닫기. `확인 중` 줄은 화면에 «아직 판단 없음» 으로 나오고(누가 확인하고 있다는 뜻이 아님) **«방에 조사 맡기기»**(주인만)가 붙는다 — 누르면 그 솔루션 대기열에 «조사·권고만» 일(ref `look:<번호>` · 선검사 안 함 · 같은 문의는 7일에 한 번)이 들어간다. 받은 방은 정해진 읽기 전용 문의 조회로 원문을 읽고, 이미 고쳐졌는지·원인을 잰 뒤, 같은 문의 확인 절차로 목록을 다시 올려 그 줄의 `verdict`·`basis`(·초안)를 고치고 권고를 보고한다. 답장·상태/승인 변경·운영 쓰기·개발은 하지 않는다.
- 맡긴 줄(답장·조사)에는 지금 어디 있는지가 붙는다: «<솔루션> 대기열 N번째»(그 폴더에서 일하는 방이 끝나야 방이 열림 — 한 솔루션 한 방) 또는 «방 <번호>».
- 나머지 = 할 일 없음(방이 처리 중이거나 볼 것만).

**«답장 보내기»·자동 답장을 받은 방이 할 일** — 그 일의 글이 정본이다. 요약: 그 솔루션의 **정해진 답글 길**(아래 «개발 명령 설정» 의 `답글 길`)로만 · 시험 실행 → 적용 · «닫기» 가 붙은 일이면 같은 길로 완료로 닫음(닫는 길이 없으면 상태는 두고 보고) · 아니면 상태는 안 바꿈 · 초안 속 사실이 운영 기록과 다르거나, 그 뒤 고객이 새 글을 썼거나, 그 종류에 답글 길이 없으면 **보내지 않고 ⏸**. 같은 초안은 상황판이 두 번 넣지 않는다(초안이 바뀌면 다시 맡길 수 있음).

솔루션 `CLAUDE.md` «개발 명령 설정» 에 이 두 줄을 채운다(새 틀엔 있음 — 옛 설치본은 없으면 더함):
```
- 운영 문의 읽기(읽기 전용): <조회 명령 — 없으면 없음>
- 답글 길: <고객 답글을 다는 정해진 명령 — 시험 실행 인자 포함. 없으면 «없음 — 관리자 화면에서 주인이 직접»>
```

## 4. 방이 상황판에 올리는 것 — 한눈에

| 하고 싶은 것 | 주소 | 핵심 |
|---|---|---|
| 주인에게 묻기 | `POST /api/asks` | 굵은 «…?» 질문 하나 · 선택지·결과·권고 |
| 이 방 일에 필요한 주인 행동(명령 붙여 넣기·우리 화면 설정) | `POST /api/asks` + `"act":true` | `steps`·`links`·`terminal` · 주인이 «했어요» 하면 같은 방이 확인하고 마무리 |
| 이 방 일과 따로 노는 주인 할 일(외부 서비스 화면 등) | `POST /api/todos` | `apart`·`after`·`waitFor` 중 하나 필수 · `then` 은 이 대화 없이도 이어갈 수 있게 |
| 독립 검증 모델 한도로 못 부름 | `POST /api/fable-wait` | 풀리면 상황판이 이 방을 깨움 |
| 문의 목록 | `POST /api/inquiries` | 3절 |
| 다른 솔루션·서버 방에 일 넘기기 | `POST /api/rooms` `{"queue":true}` | 방은 대기열에만 넣을 수 있음 |
| 배포 막기(이 일이 끝날 때까지) | `POST /api/deploy-hold` | `deploy` 가 등록된 솔루션은 상황판이 배포 — 방은 준비·막기만 |

모든 쓰기는 머리글 `Origin: http://localhost:<포트>` 가 있어야 한다. 방이 누를 수 없는 버튼(배포 승인·정기 점검 고치기·문의 답장 맡기기 등)은 403 — 우회하지 않고 주인에게 남긴다.

## 6. 새 솔루션을 더할 때 (서버 방)

1. 솔루션 폴더에 `CLAUDE.md`(틀: `kit/templates/<lang>/solution-CLAUDE.md`) · `.claude/commands/`(없는 것만) · 작업기록(틀: `kit/templates/<lang>/solution-session-state.md` — `{{NAME}}`·`{{DATE}}`·`{{OWNER}}` 채워 stateFile 경로에) — 이미 있는 것은 덮지 않는다.
   - Docker 솔루션(PM2 없음)은 «개발 명령 설정» 의 «실행 방식» 을 Docker 예시로 — 컨테이너 이름·sudo 묶음 명령·시험 명령. projects.json 은 같다(상황판은 PM2 를 보지 않음).
   - 방이 원본 폴더에서 일하는지 확인: `~/.claude/settings.json` 의 `worktree.bgIsolation` 이 `none` 이어야 원본의 커밋 안 한 변경을 방이 본다(`kit/verify.sh` 가 보여 줌 · 비어 있으면 방마다 별도 가지에서 일함).
2. `projects.json` 에 한 줄(2절 — 처음엔 `noDevDone:true`, `prodLabel:null`).
3. 그 솔루션 방에 «개발 명령 설정 절 채우기(빌드·재시작·주소·문의 읽기·답글 길·배포)» 를 대기열로.
4. 명령이 생긴 버튼만 켜고 `kit/verify.sh`.

## 7. 개발 서버 → GitHub 올리기 (배포 키)

솔루션 저장소 하나에만 쓰는 열쇠(Deploy key, 쓰기 권한)로 올린다 — 사람 계정 열쇠·토큰을 서버에 두지 않는다. 저장소마다 열쇠 하나.

1. **열쇠 만들기**(서버 방 · 솔루션마다): `ssh-keygen -t ed25519 -N "" -f ~/.ssh/<이름>_deploy -C "<서버 이름>-<저장소>"` → 지문 `ssh-keygen -lf ~/.ssh/<이름>_deploy.pub` · 공개키 `cat ~/.ssh/<이름>_deploy.pub` (비밀키 파일은 어디에도 붙이지 않는다)
2. **저장소 관리자에게 요청**(주인이 직접 하거나 관리자에게 보낼 글 — 이 틀 그대로):
   ```
   저장소: <조직>/<저장소>
   Deploy key 추가 — Title: <서버 이름>-<저장소>
   공개키: ssh-ed25519 AAAA… <서버 이름>-<저장소>
   공개키 지문: SHA256:…   (받은 키가 이 지문인지 확인 부탁)
   Allow write access: 체크 (서버가 올리는 쪽)
   보호 브랜치: main 은 보호 유지 — 서버는 <브랜치>(예: dev) 에만 올리고 main 은 PR 로
   ```
   GitHub 화면: 저장소 → Settings → Deploy keys → Add deploy key
3. **솔루션 저장소에 열쇠 지정**(그 저장소에만 적용 · 경로는 절대 경로):
   ```bash
   git -C <솔루션 폴더> remote set-url origin git@github.com:<조직>/<저장소>.git
   git -C <솔루션 폴더> config core.sshCommand "ssh -i $HOME/.ssh/<이름>_deploy -o IdentitiesOnly=yes"
   ssh-keyscan -t ed25519 github.com >> ~/.ssh/known_hosts   # 처음 한 번 — 나온 지문을 GitHub 공개 지문과 비교(docs.github.com «GitHub's SSH key fingerprints») · 백그라운드 방은 «yes/no» 질문에 답할 수 없음
   ssh -i ~/.ssh/<이름>_deploy -o IdentitiesOnly=yes -T git@github.com   # «Hi <조직>/<저장소>! …» 면 열쇠 OK (이때도 끝 번호는 1 — 실패 아님)
   git -C <솔루션 폴더> push --dry-run origin <브랜치>
   ```
4. **작업방 허락 규칙** — Claude Code auto 모드의 자동 판정은 «배포 키로 GitHub 에 붙는 것» 을 막을 수 있다(방이 push 에서 멈춤). 그 솔루션의 `<솔루션 폴더>/.claude/settings.local.json`(git 에 안 올라감 · 이미 있으면 `permissions` 에 더하기)에 허락 규칙을 넣는다. 그 파일이 `.gitignore` 에 들어 있는지 먼저 확인(없으면 `.claude/settings.local.json` 한 줄 더하기 — `/개발완료` 는 `git add -A` 라 안 그러면 올라감):
   ```json
   {
     "permissions": {
       "allow": [
         "Bash(git push origin <브랜치>)",
         "Bash(git push --dry-run origin <브랜치>)",
         "Bash(ssh -i ~/.ssh/<이름>_deploy -o IdentitiesOnly=yes -T git@github.com)"
       ],
       "deny": ["Bash(git push --force*)", "Bash(git push -f*)", "Bash(git push * --force*)", "Bash(git push * -f*)", "Bash(git push * +*)", "Bash(git push * main*)", "Bash(git push *:main*)", "Bash(git -C * push*)"]
     }
   }
   ```
   허락은 정해진 브랜치 push 만. 금지 규칙은 «한 번 더 막는 것» 일 뿐 — main 을 지키는 진짜 장치는 2단계에서 요청한 GitHub 보호 브랜치다. 주인이 직접 넣는다(방이 자기 허락 규칙을 넓히지 않는다).
5. **«개발 명령 설정» 의 push 줄을 맞춘다**: `- push: 개발완료 때 push 함 · 명령 git push origin <브랜치> · 올리는 브랜치 <브랜치> · 열쇠 배포 키 ~/.ssh/<이름>_deploy (core.sshCommand)`. `/개발완료` 가 이 줄대로 올리고, 막히면 우회하지 않고 보고에 «push 안 됨 — 오류 한 줄».
6. 열쇠를 바꾸거나 서버를 옮기면: 관리자에게 옛 키 지우기 요청 · `~/.ssh/<이름>_deploy*` 지우기.
